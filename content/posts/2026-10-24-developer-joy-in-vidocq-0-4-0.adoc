A runtime can boot in 130 milliseconds and still lose a new user in the first ten minutes. That is not spent in the
runtime. It is spent in the pom, in `module-info.java`, in a warning nobody explains, in a command that works one
way and its Maven twin another. Vidocq 0.4.0 is the release where we went after those ten minutes.

This post tells how. First we made the CLI and the Maven plugin one tool. Then we audited the result with the eyes
of someone who has never seen Vidocq, found eleven bugs we did not like, and changed what an application has to
carry. At the end, the session you get with 0.4.0-RC1, command by command.

== Where we started: two tools that disagreed

Vidocq has always had two front doors. The *CLI* (`vidocq create`, `vidocq dev`, `vidocq extension add`…) is the
one the getting-started guide shows. The *Maven plugin* (`vidocq:dev`, `vidocq:generate`, `vidocq:jlink`…) is the
one the build actually runs, in CI and in your IDE.

Up to 0.3.0 they overlapped by accident rather than by design, and in August a user showed us where it hurt. They had
taken the Vidocq parent out of their pom, copied the compiler and plugin configuration into their own, and the
packaged application ran fine. `vidocq dev` did not:

[source]
----
WARNING: No Vidocq extensions discovered
----

The reason was embarrassing and simple. `vidocq dev` and `vidocq start` booted the runtime from *the CLI's own
module path*. They never read the pom, so the extensions the project declared were never there. The packaged
launcher worked because the plugin built it from the project. Two tools, two answers to "which extensions does this
application run with?".

That report (https://codefloe.com/Vidocq/vidocq/issues/47[vidocq#47]) is the seed of everything below. Thanks again
to its author, who came back two months later to confirm the fix on a snapshot.

== Step one: one implementation, two front doors

The fix for #47 was to stop the CLI from pretending to be a runtime. Since 0.4.0, `vidocq dev` runs `vidocq:dev`
in your project, and `vidocq start` runs `vidocq:run`, with `./mvnw` when the project has one. The plugin
resolves the project's dependencies, so both commands see exactly what your pom declares.

That fixed the symptom. The cause was wider: the two tools *described the same facts twice*. Which codegen bundle
goes with which extension, which `module-info` directives an extension needs, which extensions exist at all. The CLI
had a hand-written list of seven codegen bundles and a `switch` of `module-info` rules; the plugin had a naming
convention. When an extension gained a codegen bundle, the plugin saw it and the CLI did not.

https://codefloe.com/Vidocq/vidocq/issues/314[vidocq#314] removed the duplication in three layers.

*The extensions are the source of truth.* Each extension ships a small descriptor,
`META-INF/vidocq/extension.properties`: its short id, a description, its codegen bundle, and what the application's
`module-info.java` needs. The catalog both tools read is generated from those descriptors when the runtime is
built, so the CLI knows an extension before Maven has downloaded it.

*One shared module does the work.* `vidocq-runtime-tooling` holds the pom editor, the `module-info.java` editor,
the scaffolder, the `doctor` checks and the `vidocq.properties` reader. It depends on `java.xml` and nothing else.
The CLI uses it on the module path; the plugin uses it on the class path.

*Each tool is a thin adapter.* The CLI keeps its argument parser and its coloured output; the mojos keep their
`@Parameter`s and their Maven log. Between them, a three-method `Reporter` interface: success, warning, error.

.The CLI and the Maven plugin share one implementation

The result is a simple contract: *every command that edits or checks the project has a goal, and both run the same
code*. The commands that build or run the application run their goal.

[cols="2,3,3"]
|===
| CLI | Maven plugin | How they agree

| `vidocq create`
| `vidocq:create`
| The same scaffolder writes the project.

| `vidocq extension add` / `remove`
| `vidocq:add-extension` / `vidocq:remove-extension`
| The same editor writes the dependency, the codegen path and the `module-info.java` directives.

| `vidocq extension list`
| `vidocq:list-extensions`
| The same catalog, the same test for an extension jar.

| `vidocq doctor`
| `vidocq:doctor`
| The same facts, the same checks.

| `vidocq dev` / `start` / `test` / `idea`
| `vidocq:dev` / `run` / `test` / `idea`
| The command runs the goal.

| `vidocq build [jlink\|jpackage\|docker]`
| `package`, `vidocq:jlink`, `vidocq:jpackage`, `vidocq:docker`
| The command runs the build.
|===

So the CLI is a convenience, never a requirement. A team that lives in Maven, in CI or in an IDE gets every
project-level function as a goal, with the same output. A developer who likes short commands gets
`vidocq extension add knock-health` instead of `mvn vidocq:add-extension -Dextensions=knock-health`, and the same pom
edit.

== Step two: an honest audit

With the two tools agreeing, we did what we should do more often: we started from an empty directory, with the CLI
built from `main`, and ran everything a newcomer would run. `create`, `doctor`, `extension add` and `remove`,
`config`, `build`, `start`, `dev` with a live edit, `test`, `idea`, `build jlink`. Then the same again on a pom
without the Vidocq parent, the setup of #47.

The runtime side was already where we want it:

[cols="3,2"]
|===
| Measured on an Apple M5 Max, JDK 25, application `demo-app` with REST + Health | Result

| Runtime start (`vidocq start`, startup report)
| 130 ms

| `vidocq dev`, from the command to the first answer (compile included)
| about 10 s

| A source change, from saving the file to the new answer (in-JVM layer swap)
| about 3 s

| `vidocq build jlink`, then the image's own launcher: runtime start
| 133 ms (726 ms for the whole process)
|===

The first contact was not. We logged eleven bugs, each with its issue and its `BUG.md` entry
(https://codefloe.com/Vidocq/vidocq/issues/339[vidocq#339] lists them). A few of them, because they show the kind
of thing that costs a newcomer time while every maintainer has long stopped seeing it:

* `vidocq doctor` warned about a missing Maven wrapper *on the project `vidocq create` had just written*, because
  `create` wrote no wrapper.
* The created application took the runtime's version: `demo-app-0.4.0-SNAPSHOT.jar`.
* The created pom carried two workarounds, with comments, for bugs of 0.2.0 fixed months ago.
* `vidocq create --name demo-app` wrote a class called `DemoAppApp`.
* Every build printed three javac warnings, and a note telling you to add a `provides` to `module-info.java` that a
  Vidocq application does not need.
* The catalog described `mansart-data` as Jakarta Persistence; it is Jakarta Data.
* `vidocq extension add mansart-persistence` wrote a coordinate that does not exist, because that extension had no
  descriptor.
* On a pom without the Vidocq parent, `extension add` warned that the Vauban indexer was dropped, while the pom
  listed it and the build was right.

None of them breaks a running application. All of them make a first project look less finished than the runtime
under it. 0.4.0-RC1 fixes all eleven, each with a test that would have caught it.

The audit also showed something no single bug captures: *how much configuration an application carries*. Adding
REST to an application meant three places. A dependency. A codegen bundle in the compiler's
`<annotationProcessorPaths>`, with `combine.children="append"` so the inherited Vauban indexer survives. And eight
lines of `module-info.java`. We had three plugin goals (`checkpom`, `check-module-info`, `complete-module-info`) whose
job was to police that configuration. Tools that check what you wrote are good; not having to write it is better.

=== An application BOM, and a parent made for applications

Until now, a created application inherited `vidocq-runtime-parent`, the parent of the runtime's *own* build. It
worked, but your application got our CI settings, our SonarQube configuration and the TCK list of our repository.

0.4.0 separates them:

* `vidocq-runtime-bom` manages the version of every artifact an application may declare: the runtime, every
  extension, its codegen bundle, its dev-console companion, the test support. Import it, and your pom names
  extensions without versions, with or without our parent.
* An application parent that imports the BOM and carries only what an application needs: the compiler release, the
  Vauban indexer, and the Vidocq plugin with its checks and packaging.

`vidocq create` uses the application parent. Teams that have their own corporate parent, like the author of #47,
import the BOM instead.

[source,xml]
----
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>io.vidocq.runtime</groupId>
            <artifactId>vidocq-runtime-bom</artifactId>
            <version>0.4.0</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
----

=== The codegen bundle follows the dependency

Vidocq does at build time what other runtimes do at startup: Vauban indexes your beans and generates their proxies
with an annotation processor, and extensions such as REST or Jakarta Data add their own processors. That is where
the 130 ms come from, and it is not negotiable. Making you write it twice is.

With 0.4.0, the Vidocq plugin, declared as a build extension, puts the codegen bundle of each Vidocq extension in your
dependencies on the compiler's processor path itself. Adding an extension is one dependency again, and `checkpom`
becomes a safety net rather than a daily error.

=== What stays explicit, and why

`module-info.java` stays yours. Vidocq applications are Java modules, and a module declaration that a tool rewrites
behind your back is not a declaration any more. What changed is that you never have to *guess* it:
`vidocq extension add` writes the `requires` and `opens` an extension needs, marks each line with
`// vidocq:<id>`, and `vidocq extension remove` takes exactly those lines out again.

[source,java]
----
module io.example.demo.app {
    requires io.vidocq.runtime.core;
    requires io.vidocq.runtime.extensions.jakartaee.core.cassini; // vidocq:cassini-rest
    requires jakarta.ws.rs; // vidocq:cassini-rest
    requires io.vidocq.runtime.extensions.microprofile.knock; // vidocq:knock-health
    opens io.example.demo.app; // vidocq:cassini-rest
}
----

=== A doctor that looks at the project

`vidocq doctor` used to check your machine: JDK, `JAVA_HOME`, wrapper, a pom, configuration keys. Useful, but the
questions newcomers actually ask are about the project. Why does my REST resource answer 404? Why does this extension
not start?

In 0.4.0, `vidocq doctor` (and `vidocq:doctor`, same code) also checks that every extension has its codegen and the
Vauban indexer, that `module-info.java` declares what the extensions need (read from the source, before any
compile), that Maven is the pinned version, that the HTTP port is free, and that the CLI is up to date. Each problem
comes with the command that fixes it, and `vidocq doctor --fix` applies the fixes the tooling knows how to make.

== Your first ten minutes with 0.4.0-RC1

// DRAFT(#339): run this whole section on the RC1 build and paste the real outputs.

Install the CLI. It is a self-contained distribution from Maven Central; no Maven involved:

[source,bash]
----
curl -fsSL https://vidocq.dev/install.sh | sh
----

Create an application with REST:

[source,bash]
----
vidocq create --name todo -g com.example -x cassini-rest
cd todo
----

You get a pom on the application parent with your own version, a `module-info.java`, a REST resource, a
`vidocq.properties`, a first test that boots the application and calls the resource, a Maven wrapper, a
`.gitignore` and a README. `vidocq doctor` has nothing to say:

[source,bash]
----
vidocq doctor
----

Start dev mode, open the dev console on `http://127.0.0.1:8888/`, and edit `HelloResource`: the next request
answers with your change about three seconds after you save.

[source,bash]
----
vidocq dev
----

In a second terminal, keep the tests running on every change:

[source,bash]
----
vidocq test
----

Add health checks: one command, and the pom and `module-info.java` are both right.

[source,bash]
----
vidocq extension add knock-health
----

Ship a self-contained image that brings its own trimmed JDK:

[source,bash]
----
vidocq build jlink
./target/dist/bin/todo
----

And if your team prefers Maven alone, every step above has its goal, from `vidocq:create` to `vidocq:jlink`.

== What is next

The registry behind `vidocq extension list --available` is the catalog shipped with your CLI; a live catalog belongs
with the web project initializer we want at `start.vidocq.dev`
(https://codefloe.com/Vidocq/vidocq/issues/17[vidocq#17]). IntelliJ run configurations (`vidocq idea`) are still
experimental. And we will keep doing the empty-directory audit before every release, because the bugs it finds are
the ones we no longer see.
