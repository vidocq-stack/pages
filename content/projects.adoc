= Vidocq Projects

Vidocq is one repository, link:https://codefloe.com/Vidocq/vidocq[Vidocq/vidocq], released under one version.
Each component implements one Jakarta or MicroProfile specification, or one foundational concern, and publishes its
own artifacts to Maven Central: an application takes only the layers it needs, and a brick also runs on another CDI
container or application server.

The dependency graph is strictly layered: foundational bricks have no dependency on each other;
Jakarta layers compose bricks; MicroProfile layers sit on top.

Vidocq's home ground is the Core Profile and MicroProfile. Its Jakarta EE Web Profile side (Servlet, Pages,
Expression Language, Tag Library, WebSocket, Security, Persistence) is a *preview* in 0.4.0: usable and released, with
official TCK runs behind each brick, but not complete and not certified. Noether and Kerckhoffs sit in the
repository's `preview/` folder.

== Foundational Bricks

These four components have zero inter-dependencies and carry no external runtime libraries.
They are the stable base everything else builds on.

=== `chappe` — HTTP Server

Pure Java 25 HTTP/1.1 and HTTP/2 transport layer, with first-class **WebSocket** (RFC 6455)
and **gRPC** transport (core framing over HTTP/2). HTTP/3 is on the roadmap, pending the JDK QUIC stack.
Handles connections, request parsing, and response serialisation with no third-party I/O framework.

It is built on the pure one-virtual-thread-per-connection model. Measured figures, with their
hardware and exact commands, are recorded in
link:https://codefloe.com/Vidocq/vidocq/src/branch/main/vidocq-components/vidocq-components-transport/chappe/BENCH.md[Chappe's BENCH.md].

=== `vauban` — CDI Container

CDI 4.1 Lite container, Java Modules native.
Uses the Class-File API and APT processors to generate bean metadata at compile time —
no runtime scanning, no reflection. Build compatible extensions run once, at build, and the start replays what they
did. Vauban Naming answers JNDI `java:` lookups from the container.

=== `champollion` — JSON & Protobuf Processing

Jakarta JSON-P 2.1 and JSON-B 3.0 implementation.
Produces JSON-B adapters and serialisers statically at build time.
Also provides **Protocol Buffers** support, generating message codecs at compile time —
the serialisation backend for `chappe`'s gRPC transport, with no external protobuf runtime.

=== `ravel` — Configuration

MicroProfile Config 3.1 implementation.
Sources: environment variables, system properties, and `META-INF/microprofile-config.properties`.

== Jakarta EE Layer

=== `cassini` — Jakarta REST 4.0

Jakarta REST implementation.
Resource scanning and provider registration are handled at compile time via APT, keeping
startup time flat regardless of application size. A REST application can also run as a plain servlet, through the
`cassini-servlet` module.

=== `foy` — Jakarta Servlet 6.1 and WebSocket 2.2 (preview)

Servlet container bridging `chappe` for transport and `vauban` for CDI integration: filters, listeners, sessions,
multipart, security constraints with BASIC and FORM login. It also brings the Jakarta WebSocket 2.2 server API.

=== `peano` — Jakarta Expression Language 6.0 (preview)

The engine behind `${...}` and `#{...}`, on the `jakarta.el` API alone. A page reads a `@Named` bean without
reflection.

=== `ibarra` — Jakarta Pages 4.0 (preview)

JSP pages compiled at build time: `vidocq:generate` compiles them into the application module, so no work is left
for the start, and a page that does not compile fails the build instead of the first request that asks for it. Runs
on `foy` with `peano`.

=== `bodoni` — Jakarta Standard Tag Library 3.0 (preview)

The `c:`, `fmt:`, `fn:`, `x:` and `sql:` tags, as tag handlers on the Tag Library API alone; Ibarra can inline them at
build time.

=== `kerckhoffs` — Jakarta Security 4.0 (preview)

Authentication under Jakarta Security on the Servlet extension: identity stores, the BASIC and FORM mechanisms, your
own mechanism, `SecurityContext.authenticate` and `@RememberMe`. Not complete yet.

== MicroProfile Layer

=== `heisenberg` — Fault Tolerance 4.1

`@Retry`, `@CircuitBreaker`, `@Bulkhead`, `@Timeout`, and `@Fallback` over virtual threads.
No thread-pool per policy; each interceptor submits to the shared virtual-thread executor.

=== `cervantes` — JWT 2.2

MicroProfile JWT: bearer token verification and `JsonWebToken` injection, signed and optionally encrypted tokens.
Uses `champollion` for JSON parsing and `java.security` for the cryptography; no third-party JWT library.

=== `cyrano` — Rest Client 4.0

Typed REST client generated at compile time from `@RegisterRestClient` interfaces.
Built on `cassini` and `chappe`; no dynamic proxies at runtime.

=== `dirac` — Metrics 5.1.1

MicroProfile Metrics: counters, gauges, timers, and histograms exposed over a `/metrics` endpoint.

=== `grimm` — OpenAPI 4.2

MicroProfile OpenAPI: generates the OpenAPI 3.1 document from Jakarta REST resources during the build
via APT, then serves it statically at runtime.

=== `humboldt` — Telemetry 2.2

MicroProfile Telemetry: distributed tracing, metrics, and logs through OpenTelemetry.

=== `knock` — Health 4.0

MicroProfile Health: liveness and readiness probes at `/health/live` and `/health/ready`.

== Persistence and Transactions

=== `mansart` — Jakarta Data 1.0 + Transactions 2.0 + JDBC

Repository pattern and transaction management with a built-in JDBC connection pool, XA connections included.
Two database dialects are supported out of the box: **H2** and **PostgreSQL**. The pool validates idle connections
and puts back what a borrower changed; a two-phase commit reaches every resource, even when one of them fails.

The H2 integration also showcases Vidocq's JAR-enrichment capability: a dedicated **H2 extension**
repackages the upstream H2 driver as a proper **Java module** — adding a `module-info` and clean
exports to a library that ships only as a classpath JAR — so it fits the strict module graph
without `--add-opens` or automatic-module fallbacks.

=== `noether` — Jakarta Persistence 3.2 (preview)

Jakarta Persistence on Mansart's pools and transactions, as a Vidocq extension: `persistence.xml` units or
`vidocq.persistence.*` keys, `@PersistenceContext` and `@Inject`, a connection shared with Mansart Data repositories
within a transaction, and a dev console panel that draws your model and runs your JPQL.

== Orchestrator

=== `vidocq-runtime` — The Vidocq runtime

Runtime orchestrator and extension SPI.
Inspired by the Quarkus extension model: extensions declare their dependencies, contribute
configuration, and wire the other bricks together at startup. It also brings the Maven plugin, the `vidocq` CLI, the
dev mode with its console, the BOM and the JNDI naming extension.

== Outside this repository

Two bricks are in development in repositories of their own, and are not released yet: `erasmus`, Jakarta Validation
3.1 with zero third-party dependency (no Hibernate Validator, no external Expression Language), and `tassis`, Jakarta
Messaging 3.1. Both will move into the repository's `incubator/` folder. Third-party extensions, such as the Vaadin
extension, live in the link:https://codefloe.com/VidocqCodeUniverse_VCU[VidocqCodeUniverse_VCU] organisation, under
the same Maven coordinates.
