= Contributing to Vidocq

Vidocq welcomes contributions at every layer of the stack: bug reports,
TCK coverage improvements, new specification implementations,
performance work, and documentation.

The source code is hosted under the https://codefloe.com/Vidocq[Vidocq organisation on Codefloe],
a https://forgejo.org[Forgejo] instance. Each specification implementation lives in its own repository.

== Two ways to take part

Everyone starts as a *contributor*: you work in your own fork of a Vidocq repository and propose
your changes with pull requests from it. After a period of contributions, the maintainers may
invite you to become a *maintainer*.

== Start here: the Vidocq workspace

Every contribution starts from the same place: the
https://codefloe.com/Vidocq/vidocq-workspace[`vidocq-workspace`] repository. It is the root
directory of all the Vidocq repositories, and holds what they share: the rules for humans and
coding agents (`AGENTS.md`), the git hooks, the https://manicli.com[mani] configuration that
clones and drives every repository, and the guides.

*Clone it and follow its
https://codefloe.com/Vidocq/vidocq-workspace/src/branch/main/docs/getting-started.md[getting-started guide].*
It takes you from a fresh machine to your first pull request, step by step, on macOS, Linux and
Windows (through WSL 2):

. your Codefloe account, your SSH and GPG keys, and your signature of the CLA;
. the tools: Git, a Java 25 JDK, mani;
. the workspace itself, cloned with all the repositories;
. the Maven configuration and a first build;
. your first pull request, from your fork.

Once your account and keys are ready, the workspace is three commands away:

[source,bash]
----
git clone git@codefloe.com:Vidocq/vidocq-workspace.git
cd vidocq-workspace
mani sync                    # clones every repository into <repo>/main/
mani run -a install-hooks    # the shared git hooks, in every repository
----

== Before your first pull request

Three automatic checks run on every pull request, in every repository. A pull request that
fails one of them cannot be merged.

[cols="1,3",options="header"]
|===
| Check | Passes when

| CLA
| you signed the Vidocq Contributor License Agreement: your Codefloe username is listed in the governance repository

| GPG
| every commit is signed with your GPG key, registered in the governance repository

| DCO
| every commit carries a `Signed-off-by:` line (Developer Certificate of Origin 1.1)
|===

You set them up once, in about twenty minutes, by following the
https://codefloe.com/Vidocq/governance/src/branch/main/README.md#one-time-setup[one-time setup]
of the https://codefloe.com/Vidocq/governance[governance repository]: it covers macOS, Linux and
Windows, with examples. The CLA lets the maintainers distribute your contribution under the
project's disjunctive triple licence:

[source]
----
SPDX-License-Identifier: EPL-2.0 OR EUPL-1.2 OR GPL-2.0-or-later
----

Contributing on behalf of your employer? Your organisation signs a Corporate CLA first: write to
mailto:contribute@vidocq.io[contribute@vidocq.io].

== Contributing from a fork

. *Fork* the repository on Codefloe, and add your fork as a remote of the clone that the
  workspace made (`+git remote add fork git@codefloe.com:<you>/<repo>.git+`).
. *Create a branch* from the latest `main`, in a worktree next to `main/`.
. *Write the failing test first*, then the implementation.
. *Prove it* with a full build: `./mvnw -ntp clean install`. If your change touches a TCK, run it
  and confirm there is no regression.
. *Commit and push* to your fork; your commits are signed and signed off automatically.
. *Open the pull request* from your fork to `main` of the Vidocq repository.
. *Follow the checks and the review.* The checks of a pull request from a fork start once a
  maintainer has approved them. If `main` moves on, rebase your branch and push it again;
  never use the *Update branch* button, which breaks the signatures.
. *A maintainer merges* your pull request once the review is done and the checks are green.

Each step, with the commands and how to fix a failing check, is in the
https://codefloe.com/Vidocq/governance/src/branch/main/CONTRIBUTING.md[contributor guide].

== Becoming a maintainer

Contributing needs no role in the Vidocq organisation: forking, opening pull requests and
signing the CLA are open to any Codefloe account. After some time contributing, the
maintainers may invite you to join them. The decision is theirs: there is no automatic
threshold. As a maintainer, you join the `devs` team of the Vidocq
organisation on Codefloe. You then work in branches of the Vidocq repositories instead of a fork,
merge your own pull requests with the `/merge` command of the merge-bot, and review the pull
requests of others, including those from forks.

From then on, you follow the
https://codefloe.com/Vidocq/governance/src/branch/main/MAINTAINERS.md[maintainer guide] of the
governance repository.

== Engineering rules

The rules are written in the
https://codefloe.com/Vidocq/vidocq-workspace/src/branch/main/AGENTS.md[`AGENTS.md`] file of the
workspace, which coding agents read too, and summarised in each repository's own `AGENTS.md`.

=== Strict Java Modules

* Every module ships a `module-info.java`.
* `exports` are minimal: only the packages of the public API.
* `opens` require a documented reason.
* No classpath mode, no automatic modules, no split packages.

=== Zero runtime dependencies

What ships depends only on the Jakarta and MicroProfile APIs it implements.
No ASM, Byte Buddy, reflection libraries, or general-purpose utilities.
Any new runtime dependency requires an explicit justification in the pull request.

=== Maximum static code generation

Prefer the Class-File API (JEP 484) and annotation processors over runtime reflection.
Metadata that can be produced at `compile` or `process-classes` time must not be computed at runtime.
This keeps startup time flat and makes native compilation with GraalVM and Leyden CDS straightforward.

=== Virtual threads for all I/O

Use `Executors.newVirtualThreadPerTaskExecutor()` for any I/O path.
Platform thread pools are only acceptable with a documented reason.
Avoid `synchronized` blocks around I/O; prefer `ReentrantLock` to prevent carrier-thread pinning.

=== Test-driven development

Write the failing test before the implementation — red → green → refactor.
The official Jakarta and MicroProfile TCKs run through Arquillian. Their runners sit behind the
`tck` Maven profile, so a normal build neither downloads nor runs them: run them with the script
at the root of the repository, for example `./run-official-tck-servlet6.1.sh` in Foy or
`./run-official-tck-restful-4.0.sh` in Cassini.

=== Toolchain

Java 25 and Maven 3.9.16. Each repository ships a Maven wrapper: always build with `./mvnw`, and
always with `clean install`, because a stale `target/` directory can hide a failure or invent one.

== Commit messages

Vidocq uses https://www.conventionalcommits.org/[Conventional Commits], in English:

[source]
----
<type>(<scope>): <short description> (#<issue>)

[optional body: what changed and why]

Signed-off-by: Your Name <your@email.com>
----

*Types:* `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `build`, `ci`, `chore`

*Scope:* the area of the repository — `http` or `tls` in Chappe, `processor` in Vauban, `core` in Foy, ...

[source]
----
fix(tls): the handshake unwraps buffered records before reading (#24)

Signed-off-by: Jane Doe <jane.doe@example.com>
----

If an AI assistant helped you write a commit, add a `Co-Authored-By:` trailer naming the tool.
You remain the author and the committer.

== Bug reports and performance changes

Any reproducible bug must be tracked in a `BUG.md` file at the root of the relevant repository:
short id, date, symptom, minimal repro, root-cause hypothesis, and status.
Include a `BUG.md` entry in your pull request if you are fixing a known bug.

Any performance number must be recorded in a `BENCH.md` file at the root of the repository:
date, hardware and JVM details, exact command, raw results, and delta versus the previous run.
Never quote performance figures in commit messages or PR descriptions without a `BENCH.md` entry.

== Language

Code, Javadoc, comments, commit messages, and all `.md` and `.adoc` files are written in *English*.

== Questions
